Product

The visualizer for XO data: a very simple dashboard that analyzes .xo project data, plus a very simple work-item tool for tracking work and progress over time. Local, single user, dark UI in Linear's style.

Context: xo-space (the FastAPI local control plane at localhost:5002) owns the .xo model. Its watcher writes the .xo files from every runtime's session logs; it bundles a Space UI (graph, projects drawers, sessions telemetry, chat, wiki) at /space; and it exposes HTTP APIs including full todo CRUD. This app is the Linear grade work tracking front end over the same data. It reads files directly today and can adopt xo-space's APIs later without changing any UI.

Principles

  • Short, tight feature list. Add nothing that is not required.
  • Read only mirror of .xo files; the app never writes to them.
  • One feature = one prompt = one small diff. Expand specs only on ask.
  • Data model changes go through lib/types.ts and lib/store.ts actions.

XO data inventory, what exists to visualize

Per project folder, .xo/ holds:

  • project.json: identity plus classification (category, ptype, file counts and extensions, last_touched)
  • stats.json: rolling 7d and 30d token usage by model, tool calls, files edited, sessions, active minutes; by_session and by_day series
  • timeline.jsonl: session.started, file.created, file.edited, todo.added, todo.completed events with ts, session_id, project_id
  • todos.json and sessions/ metadata

The root .xo/ adds: workspace.json (project list plus folder classification clusters), work-items.json, quirqs.json (budget per work item), activity.json (open sessions). Shared projects also carry peers.json and sync.json.

Facts from xo-space, the source of truth: the .xo files are written by its watcher (agents never write them directly); JSON Schemas for every file live in xo-space/services/cowork_agent/visualizer/schema/; todo statuses are pending, in_progress, completed, cancelled, blocked; the canonical projects root is ~/xo-projects (AGENTS.md, PROJECT.md, OBJECTIVES.md, PLAN.md, PROGRESS.md, memory/, .xo/ per project); and HTTP APIs exist, including todo CRUD at /api/xo-projects/{id}/todos.

Mirrored today: todos, work items, project names. The rest is untapped. If write back is ever promoted, the safe path is xo-space's todo API, never writing .xo files ourselves.

Components, a user manual

disk .xo files, source of truth, read only local localStorage, survives reloads memory this tab only, lost on reload or sync derived computed from the above

.xo data source disk

What: todos.json (agent session todos) and work-items.json (operator work items), from the root and each selected project folder.

Interact: not editable in the app; sync via Refresh from XO or a reload.

Expected: every sync rebuilds issues, projects, members and tags; in-app edits to mirrored data disappear on the next sync.

Setup local

What: picks the XO root and which top level folders count as projects.

Interact: sidebar footer, workspace menu, or Cmd K; edit root, Load, tick folders, Save and sync.

Expected: root falls back to XO_ROOT env, then the topmost folder above the app containing .xo; folders with their own .xo show a badge.

Projects derived

What: each selected folder plus the root as Workspace; sidebar entries expand into Work items and Sprints.

Fields: id, name, folder (empty string means the workspace root), color. Workspace identity: name, teamKey (the XO-n prefix), teamName, color.

Interact: expand or collapse; New issue from a project view pre-fills that project.

Expected: work items route by folder, and by project_id for root level items.

Work items (issues) memory

What: every todo and work item mirrored as an issue, numbered XO-n, grouped by status.

Fields: id, number, title, description, status, priority, assigneeId, labelIds, projectId, sprintId, objectiveId, estimate, dueDate, createdAt, updatedAt, origin (kind, sourcePath, sessionId) on mirrored issues. Status: backlog, todo, in_progress, in_review, done, canceled. Priority: none, urgent, high, medium, low. Estimate: 1, 2, 3, 5 or 8.

Interact: open detail; edit status, priority, assignee, tags, sprint, OKR, estimate, due date; create with C; delete from detail. Mirrored issues also show an Origin panel: kind, session id and source path (copyable), and agent todos get a Watch replay link that opens space-walk on that session.

Expected: pending maps to Todo, in_progress to In Progress, completed to Done, else Backlog; numbers can shift between syncs.

Tags (labels) derived

What: two fixed source tags, Agent todo and Work item, auto applied by the mirror.

Fields: id, name, color.

Interact: filter in the issues filter bar; assign or remove in pickers (memory).

Expected: no user created tags yet; promote via Requests if needed.

Sprints local

What: timeboxed batches, workspace wide; each project's Sprints view scopes them to that project's issues.

Fields: id, number (sequential), name ("Sprint N"), goal (optional), startDate and endDate (ISO, inclusive).

Interact: create with goal and dates, edit, delete; assign issues via pickers (assignments on mirrored issues are memory).

Expected: active, upcoming or completed derives from dates; completion is done over non-canceled.

OKRs local

What: objectives with key results, health, owner and target date.

Fields: objective: id, name, description, ownerId, health (on_track, at_risk, off_track), targetDate, keyResults, createdAt. Key result: id, name, current, target, unit ("%", "min").

Progress math: key result progress is current over target capped 0 to 100; when target is below current the ratio inverts so decreasing targets (latency, cost) work; target 0 scores 100 only when current is 0. Objective progress is the plain average of its key results.

Interact: create, add or edit key results, set health, link issues (links on mirrored issues are memory).

Expected: progress is the average of key result progress; decreasing targets supported.

Wiki local

What: markdown docs with mermaid diagrams. System docs: XO data flow, Anatomy of .xo and xo.json, PRD.

Fields: id, title, content (markdown subset), authorId (null for system docs or removed authors), createdAt, updatedAt.

Interact: create, edit as raw markdown, delete.

Expected: system docs refresh on version bumps; the PRD doc mirrors PRD.md from disk each sync, so edit the file, not the doc.

Members memory

What: people derived from work item creators and owners, plus the operator.

Fields: id, name, email, role (Admin or Member), color, joinedAt.

Interact: invite adds a member; removing one unassigns their issues.

Expected: invites vanish on the next sync; Workspace operator stands in for the signed-in user, so My Issues includes all agent todos.

Calendar derived

What: month grid of sprint spans, OKR target dates and issue due dates.

Expected: mirrored issues carry no due dates yet, so entries come mostly from local sprints and OKRs.

Inbox and My Issues derived

What: Inbox is a notifications placeholder; My Issues filters to the current member.

Expected: Inbox stays empty until notifications get promoted out of non-goals.

Command palette and hotkeys

What: Cmd or Ctrl K: navigate, search issues, docs, sprints and OKRs, New issue, Refresh from XO, Setup. C creates an issue from anywhere.

Expected: search matches titles; actions close the palette.
